# Native runtime rebuild

Started 27 September 2026 on `codex/sage-runtime-rebuild`, from the existing v2 working tree. This ledger tracks implementation, not production qualification. The current source architecture and source map are in the [canonical architecture guide](../architecture.md).

The user's goal is a substantially more capable, faster, reliable laptop agent, built at the runtime/OS boundary rather than assembled as a superficial workflow. Acceptance covers all three requested groups: documents/browser/app control; coding/terminal/debugging; files/settings/background automation. No universal superiority or zero-harm claim can be inferred from unit tests. Capabilities must be demonstrated against real tasks and adversarial/failure cases on their advertised platforms.

## Architecture work

The [3 October upgrade checklist](upgrade-plan.md) tracks the full October review, its P0–P3 migration requirements and all sixteen proposed product capabilities. The current pass adds native presentation/refresh improvements, independent outbound IPC, bounded read batches, cross-turn ordering and retrieval/schedule fixes. It leaves the full goal active; partial progress does not close the architecture or production gates. ## Review coverage

The architecture guide describes current source and unimplemented boundaries. This ledger records runtime changes and their evidence; passing a checkpoint does not qualify the full product or close the remaining platform and release gates.

## Acceptance layers

1. Deterministic unit/property and protocol conformance checks.
2. Integration tests using temporary files, isolated workers and scripted adversarial providers.
3. Fault injection for crash boundaries, cancellation, stale state, conflicting edits and lost acknowledgements.
4. Real local/cloud model and native OS/browser flows for all three benchmark groups.
5. Resource/latency/privacy/first-use measurements on advertised hardware and platforms.
6. Installed, signed builds and authenticated update/recovery evidence.

The goal stays active while required implementation or evidence is missing. Unsupported/high-impact operations must remain honest and constrained while their actual native execution and verification are built; a permanent reduction of scope is not the intended final product.

## Foundation checkpoint, 27 September

- **Execution evidence:** the completion reducer distinguishes answered, verified actions, partial failure and uncertain work. Fabricated success prose after failures cannot promote the task or become a success memory. This establishes action evidence; it does not prove that an arbitrary natural-language goal was completely fulfilled.
- **Acceptance and reconnect:** task, initiating message, conversation link, first event and command receipt commit together. The inbox binds a request UUID to its original payload and task ID. Tests cover 24 concurrent retries, database reopen, a lost IPC receipt, payload mismatch and a forced failure on the final transaction insert. Native transports allocate sequence at transmission; clients retain bounded submission identities across connection loss. The client outbox is still volatile across app restart. Transient storage/queue errors retain its identity because an earlier attempt may have committed.
- **Decisions:** opening a decision commits its waiting task, immutable prompt and event together. A response commits before it reaches the executor; cancellation and restart close pending authority. Questions appear in reconnect snapshots. Both clients now queue decisions, provide Stop inside prompts, and allow Later with a visible return action. Core tests cover multiple simultaneous questions, wrong-task and replayed replies, cancellation, expiry, atomic failure and restart. Native UI behavior is not yet live-qualified.
- **Responsive command handling:** ordinary and control commands have separate bounded queues. The authenticated reader no longer waits for a provider test to finish. A protocol fixture stalls the ordinary command, fills its queue, then verifies Stop and Ping before releasing it. One local run measured 3.27 ms; this is fixture latency, not a production guarantee or OS cancellation measurement. Synchronous database/filesystem work and slow peer writes still require separate treatment.
- **Content fidelity:** persistence redaction preserves non-secret indentation, whitespace, Unicode and line endings. Secret-span regression tests pass.

Evidence is saved in [the foundation evidence directory](evidence/2026-09-27-foundation/manifest.json): 59 Rust core tests passed in the workspace suite; workspace Clippy passed with warnings denied; the standalone Swift transport/retry stress test passed. The macOS runtime sources, including AppModel and the native adapter, type-check with the pinned SwiftProtobuf dependency rebuilt for the installed compiler. The complete SwiftUI app cannot currently be validated because the installed SDK lacks its `SwiftUIMacros.StateMacro` plugin. Windows compilation/runtime and the three real-task benchmark groups remain unverified.

The next control milestone is worker cancellation and late-result reconciliation. Receipt deduplication prevents repeated submissions; it does not by itself stop an OS operation already dispatched or establish exactly-once external effects.

## Worker cancellation checkpoint, 28 September

- **Worker control:** macOS and Windows readers launch session-owned operations instead of awaiting them. Stop cancels those operations through a reserved protocol message; disconnect cancels the session. The browser native host reads core and extension frames concurrently, with bounded queues, correlation maps and write deadlines. The extension processes cancellation outside its action queue and checks it immediately before navigation. Acknowledgements mean the signal was received, not that an external effect was prevented.
- **Late evidence:** the broker keeps cancelled identities until the acknowledgement and final reply arrive, suppresses requests cancelled before IPC dispatch, and rejects wrong-session or duplicate replies. Effect replies commit to bounded private artifacts before waking the original waiter. Late receipts mark the action uncertain rather than promoting a worker's success assertion to verified success. Resume refuses outstanding effects. Full postcondition reconciliation, explicit stopping/settled UI states and the larger transactional reducer remain open.
- **Bounded admission:** registering and enqueuing a worker request cannot suspend midway. Queue saturation is rejected before creating a pending identity. Native registries and browser queues are bounded; control capacity exhaustion disconnects its authority scope. Underlying OS calls may ignore cooperative cancellation, so disconnect is not proof that all effects stopped.
- **Forgotten content:** forgetting related memory durably revokes subsequent artifact retention for affected runs. A late worker receipt keeps opaque accounting but cannot recreate its deleted body. Outcome projection is serialized with forgetting. Broader artifact purposes, Undo retention and full deletion semantics still need redesign.

Evidence in [the worker cancellation directory](evidence/2026-09-28-worker-cancellation/manifest.json) records 63 Rust core tests plus the browser relay test, six extension fixture tests, workspace Clippy with warnings denied, standalone Swift transport/cancellation checks, and the macOS runtime type-check. These are protocol/runtime fixtures. Full macOS UI, Windows execution, browser installation, actual OS cancellation and all three real-task benchmark groups remain unverified.

The next implementation step is to commit verified action state, result, evidence, event and audit records together, and apply the same reducer during recovery. The cancellation checkpoint does not qualify the full runtime or production behavior.

## Verified transition checkpoint, 28 September

- **Atomic evidence:** the new `transitions.rs` reducer validates the current action and fresh observation, builds its matching result, and commits journal verification, returned-content artifact, task/action projection, success event and audit link in one SQLCipher transaction. The IPC event is published only after commit. A failure to advance the external audit checkpoint stops the run without downgrading its already verified action.
- **Recovery:** re-observing an uncertain effect now creates a durable `Confirmed` tool result through that same reducer. Merely setting `ActionStatus::Succeeded` was insufficient because the completion reducer requires matching evidence. Recovery rejects an action that no longer matches its prepared identity; an ordinary execution cannot overwrite an already confirmed journal entry.
- **Forgetting:** retention revocation is checked inside the transaction. If forgetting wins before commit, the reducer keeps effect evidence and an opaque notice, removes returned content, and does not recreate an artifact.
- **Fault evidence:** injected failures at artifact, task, action, event and audit writes leave all verification records uncommitted. Separate child processes exit without transaction destructors after journal, artifact, task, event, audit and final commit. On reopening, each pre-commit case has no partial verification; the committed case retains the result, artifact, event and audit link. Restart never automatically resumes a run. These process-exit fixtures do not establish resilience to storage-device failure or sudden power loss.

[Transition semantics and remaining boundaries](runtime-transitions.md) explain the implemented contract. [Checkpoint evidence](evidence/2026-09-28-verified-transitions/manifest.json) contains 71 passing Rust core tests plus one browser relay test and workspace Clippy with warnings denied. Eight additional core tests include the child-process fixture entry point, not eight independent real OS scenarios.

Still required: atomic prepare/dispatch/interruption/rollback and task-finalization transitions, durable projection cursors and bounded history, off-thread blocking storage work, explicit effect-settlement UI, isolated native authority, broader capabilities, and the full real-task/platform acceptance matrix. This checkpoint does not close the remaining transaction and recovery gaps or the overall rebuild.

## Dispatch and revision checkpoint, 28 September

- **One durable phase change:** preparation, dispatch and interruption now each commit their journal state, task/action projection, event and audit link together. Dispatch revalidates the prepared digest and grant before admission. The former standalone journal mutation methods are available only to test fixtures.
- **Stale-write rejection:** tasks carry monotonic revisions. The shared transaction writer rejects an older projection and advances the caller's revision only after commit. This applies to command acceptance, decisions, ordinary updates, recovery and the new action transitions. A verified result prepared before Stop cannot overwrite the newer cancelled task.
- **Retry truth:** the interruption transaction reads the durable journal to decide whether an effect may have executed. A misleading Failed action projection cannot make a dispatched effect retryable. Persistence failures stop automatic retries; error finalization keeps possibly executed work interrupted and revokes capabilities before storage writes.
- **Evidence:** [this checkpoint](evidence/2026-09-28-dispatch-revisions/manifest.json) records 73 passing Rust core tests plus the browser relay test, workspace Clippy with warnings denied, injected atomic-commit failures, and stale revision/restart checks. The prior verified-transition process-exit matrix still passes; this does not add abrupt-exit coverage for every new phase.

Remaining critical boundaries include runtime Stop independent of persistence, receipt reconciliation, Undo and final outcome transactions, bounded projections, isolated native authority and all three real-task acceptance groups. The transaction gap remains open until its complete crash/effect matrix is demonstrated.

## Runtime control checkpoint, 29 September

- **Stop before storage:** authenticated command admission signals the runtime before queueing persistence, including when control/response queues are saturated. Stop skips storage unlock. The cancellation signal takes no task-cache, database or credential-store lock, and the owned future covers observation and recovery as well as model/executor waits.
- **One execution owner:** bounded leases reserve execution generations before acceptance and retain ownership through cleanup. Resume and Undo cannot overlap an older execution or its outstanding worker effects. Capability grants retain their originating signal and expire when that generation stops or finishes; reusing a task identity cannot revive them.
- **Honest failed saves:** failed Stop persistence leaves an in-memory tombstone after the future exits. Snapshots explicitly show a pending save without inventing a newer durable revision. Retrying Stop can save the state and retire the tombstone. Existing effects remain verified or uncertain according to their evidence. Startup still interrupts persisted unfinished work rather than automatically resuming it.
- **Evidence:** [this checkpoint](evidence/2026-09-29-runtime-control/manifest.json) records 80 passing Rust core tests plus the browser relay test, workspace Clippy with warnings denied, and repository checks. New fixtures include failed Stop writes, a held task-cache lock, saturated control/response queues, a stale live owner, early cancellation and grant generation retirement. A temporary-directory effect survives a stopped observation and remains uncertain.

The signal is cooperative; it cannot interrupt a synchronous OS call already executing. SQL/filesystem work can still occupy runtime threads, and a slow session write can delay a command before admission. Stop's per-action cleanup is transactional, but aggregate cleanup, receipt reconciliation, compensation and final outcome transitions still need work. Full macOS UI, Windows, installed browser/provider flows and all three real-task groups remain unqualified. The next implementation boundary is durable worker-receipt reconciliation.

## Receipt reconciliation checkpoint, 29 September

- **Durable reconciliation:** saved worker receipts now have an idempotent projection marker. One transaction commits the task/action and journal state, transport result, event, audit link and marker. Startup repairs pending projections in bounded batches before loading the cache; Resume and Undo reconcile before reading effect state. New preparation cannot replace an action with unresolved receipts.
- **Evidence boundaries:** raw replies establish uncertainty, cancellation acknowledgements establish receipt of Stop, and broker-proven unsent work establishes that no worker dispatch occurred. Fresh independent verification covers prior receipts atomically. Later transport claims cannot downgrade an already verified effect or establish success on their own.
- **Private content and accounting:** deleting a receipt artifact now clears its reference while retaining opaque effect metadata and pending reconciliation. A schema migration replaces the earlier cascading deletion without losing existing receipts. Broader artifact purposes and compensation retention remain open.
- **Fault and integration evidence:** [this checkpoint](evidence/2026-09-29-receipt-reconciliation/manifest.json) records 88 passing Rust core tests plus one browser relay test and workspace Clippy with warnings denied. It adds four transaction-write failures, four abrupt-process-exit boundaries, replay/retention/migration checks and verified-receipt coverage. The core Resume fixture reconciles a saved worker reply and independently observes an existing temporary folder before declaring success. Eight additional test entries include the child-process entry point.

Receipt projection is now durable; OS-effect settlement is still distinct. Remaining work includes shared cancellation when handing control to a new continuation, aggregate finalization, journaled Undo, isolated native authority, off-thread blocking work, bounded historical projections, broader capabilities and all three real-task/platform acceptance groups. This checkpoint does not close the remaining architecture and qualification gaps.

## Continuation control checkpoint, 29 September

- **Stable Stop, fresh execution authority:** continuations inherit a stable control scope while receiving fresh task/action budgets and capability generations. The parent's execution lease stays reserved through handoff; its normal retirement does not stop the child. Stop reaches the scope immediately, including from the original control identity after repeated handoffs. Unaccepted reservations cannot leak unsaveable Stop tombstones.
- **Atomic handoff:** the source continuation link and revision commit with the child, initiating message, conversation link, source/child events and audit link. Duplicate or stale Continue cannot create another child. Acceptance takes the cache lock before commit and has no await between commit and spawning the owned execution.
- **Durable scope cancellation:** an idempotent scope Stop and audit record are saved before task projections. Acceptance and recovery reject stopped scopes. Startup cancels unfinished scope members even when their earlier task writes failed. Both clients route Stop through the stable control ID and suppress another Resume on a continued source. Undo refuses overlap with active continuations or their outstanding worker results.
- **Evidence:** [this checkpoint](evidence/2026-09-29-continuation-control/manifest.json) records 97 passing Rust core tests plus the browser relay test, workspace Clippy with warnings denied, macOS runtime type-checking and MainView syntax parsing. Nine additional Rust test entries include one child-process entry point. Fixtures cover both Stop/acceptance orders, 128 further handoffs, failed task projections followed by restart, duplicate Continue, overlapping Undo, three transaction write failures and four abrupt-process-exit boundaries.

The MainView check is syntax-only; full macOS UI and Windows compilation/runtime remain unverified. Pre-upgrade tasks default to their own control identity rather than silently regrouping historical continuations. Shared control does not prove OS-effect settlement or compensation. The next state-authority work is journaled Undo and aggregate task finalization; native authority isolation, performance, broader capabilities and all three real-task acceptance groups remain required.

## Undo journal checkpoint, 30 September

- **Compensation state:** Undo now has prepared, dispatched, uncertain and verified records. Each phase commits its task projection, event and audit link atomically; only independently verified Undo consumes recovery metadata. After possible dispatch, recovery observes without repeating the inverse. A prepared retry revalidates the original target and backup.
- **Command and target identity:** both native clients send the exact action to undo. Duplicate commands cannot fall through to an older action. The inverse must match the service-prepared forward file operation, and backup reads require the owning task. Startup repairs available action identities in bounded batches. Nonempty folders, changed targets, changed parents, expired backups and unsupported legacy plans cannot authorize a destructive retry.
- **Current execution truth:** undone actions are counted separately from current verified actions. Unresolved inverses remain uncertain and expose Check Undo. Resume cannot reuse a compensated scope's forward execution. Dispatch invalidates the task's saved success context and recorded memory descendants; an old finalizer cannot recreate it. This does not yet provide complete causal invalidation for every derived artifact or copied result.
- **Evidence:** [the checkpoint](evidence/2026-09-30-undo-journal/manifest.json) records 111 passing Rust core tests plus the browser relay test, workspace Clippy with warnings denied, macOS runtime typechecking, MainView syntax parsing and repository checks. Fourteen added test entries include a child-process helper. Twenty-one process exits exercise seven boundaries across all three supported inverses, and sixteen injected write failures verify transaction rollback. The core folder workflow, duplicate action identities, changed-file preservation, missing backups after dispatch, audit failures, stale revisions and context invalidation are also covered.

The full goal remains active. Original filesystem metadata, atomic forward-effect/recovery registration, external writer races, artifact purpose and retention, aggregate finalization, native authority isolation, performance and broader capabilities still require work. Full macOS UI, Windows, installed browser/provider behavior and all three real-task acceptance groups remain unqualified. This checkpoint does not close the remaining architecture and qualification gaps.

## Run finalization checkpoint, 30 September

- **Atomic closure:** answer, failure, Stop and interruption now reconcile journal evidence and commit task/action state, cleanup, conversation, memory, final events, audit and the attempt-bound finalization marker together. A displayed success requires matching durable verification. Events publish after commit, and later reporting or audit-checkpoint failures cannot downgrade a committed result.
- **Recovery and late evidence:** recovery advances a persisted execution attempt. Old attempts and repeated completion cannot overwrite the current outcome. Resuming replaces the earlier assistant response and summary entry; later unverified receipts update the closed conversation in the same receipt projection. Startup repairs unfinalized interrupted/cancelled runs in bounded batches without executing tools.
- **Failure containment:** a failed finalization retains its redacted request in the 64-slot run registry while retiring execution authority. The UI projection reports unsaved final state. Resume retries persistence without calling the model again; Stop can replace the pending result. This buffer is volatile, and an uncommitted response can be lost when the process exits.
- **Evidence:** [this checkpoint](evidence/2026-09-30-run-finalization/manifest.json) records 122 passing Rust core tests plus the browser relay test, workspace Clippy with warnings denied and repository checks. Eleven new test entries include a child-process helper. Sixteen injected writes and eighteen abrupt exits cover aggregate rollback and restart repair. Core fixtures exercise failed answer storage, explicit retry, Stop replacement and post-commit audit failure; registry fixtures fill and release all 64 pending slots.

Native sources/protocol did not change, and no new native UI or Windows qualification is claimed. Scope Stop intent, external effects and the OS audit anchor remain separate boundaries. Blocking storage work, historical paging, incremental audit verification, artifact purposes/retention, filesystem semantics, native authority isolation, broader capabilities and all three real-task/platform acceptance groups remain required. This checkpoint does not close the overall goal or production gates.

## Audit performance checkpoint, 30 September

- **Bounded normal work:** audit checkpoints now verify the new tail against an unchanged connection-local verified prefix, plus at most 128 historical records per incremental checkpoint. Startup, schema changes, local audit mutations, external database commits and failed checkpoint writes require a full scan. Cloned stores serialize checkpoint writers, and deferred unlock rebinds the mutation observer. The v2 chain and protected OS anchor formats remain compatible.
- **Explicit integrity window:** every checkpoint reads the OS anchor; identical values avoid another credential write. Row hooks and SQLite counters invalidate reused proof. A rotating scrub independently checks old records, with a fixed-prefix pass requiring `ceil(prefix_rows / 128)` successful incremental checkpoints. There is no idle wall-clock scrub deadline, and this does not establish protection against arbitrary physical storage tampering or an actor controlling both stores.
- **Measured evidence:** the isolated debug probe on an Apple M3 averaged 1.346 ms for one new record plus bounded scrubbing after 10,000 records; its initial full scan took 96.309 ms. The probe uses an in-memory secret store and excludes real OS credential latency. Deterministic assertions verify the row-work bound, not a machine-dependent timing threshold.
- **Validation:** [this checkpoint](evidence/2026-09-30-incremental-audit/manifest.json) records 130 core tests plus one relay test, Clippy with warnings denied, repository checks and a separate Rust/Cargo 1.89.0 workspace/all-targets compatibility check. Eight new tests cover invalidation, corruption, concurrent appends, checkpoint-write failures, restart/unlock and bounded scrubbing. The libclang build dependency and Windows CI configuration are explicit; local YAML validation is not Windows build evidence.

[The audit contract](incremental-audit.md) describes the implementation, timings and detection boundaries. Synchronous SQL/credential latency, exclusive core writer ownership, history limits, idle scrubbing, compaction, broader capabilities and all three installed-platform task groups remain open. No single checkpoint closes the overall goal or production gates.

## Directory discovery checkpoint, 30 September

- **Usable file discovery:** the planner receives the current selected folder paths and effects as bounded untrusted data. The new native `list_directory` operation returns names and types in explicit pages under the existing Read scope. It discovers filenames before a subsequent file read; it does not traverse links or read child contents. Protected descendants and credential-path policy remain enforced.
- **Verified page identity:** each page binds its canonical target, prepared directory identity, sorted name/type snapshot, offset and continuation. A fresh independent enumeration must agree before the transaction reducer commits the returned content. Stale cursors, substituted content and evidence for a different target cannot establish success. Unicode is preserved; redacted or encoded names are marked as such rather than presented as usable paths.
- **Bounded execution:** four blocking-reader slots cover execution and observation. Cancelled readers retain their slots until the OS work exits. Enumeration caps entries, raw filename bytes, page bytes and cooperative time. Each page currently rescans the entire admitted directory, and a blocked syscall cannot be forcibly interrupted.
- **Evidence:** [this checkpoint](evidence/2026-09-30-directory-discovery/manifest.json) records 140 passing Rust core tests plus the relay test, workspace Clippy with warnings denied, repository/format checks and a Rust 1.89.0 workspace/all-targets compatibility check. Ten added tests include a real temporary-filesystem/core flow with a scripted provider: it discovers a randomly named document, reads it, and crosses the 32-action limit during a 35-page listing using a fresh continuation without repeated action approval.

[The discovery contract](directory-discovery.md) specifies page semantics, authority, cost and privacy limits. The local filesystem rejects non-Unicode names, so that codec boundary is tested directly; Linux-specific file creation and Windows execution are not claimed. Native sources/protocol are unchanged. Artifact retrieval beyond previews, opaque native-name handles, larger-directory performance, full context budgets, native UI/provider/browser qualification and all three real-task groups remain required. This checkpoint does not close the overall goal or production gates.
